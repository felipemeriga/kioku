# Event Catalog

> Audience: engineers producing events in `obol-gateway`, consuming them in
> `obol-ledger`, and reading their projections in `obol-console`. This document
> is the authoritative catalogue of every domain event: the shared envelope, and
> for each event type the exact `data` schema, its producer, its consumer(s),
> ordering and causality guarantees, idempotency behavior, and a JSON example
> using the fixed sample data.
>
> Companion reading: what the ledger *does* with `payment.settled`,
> `refund.completed`, and `payout.paid` is specified in
> [05 — Ledger Model and Invariants](05-ledger-model-and-invariants.md) and
> [06 — Money Movement and Fees](06-money-movement-and-fees.md); the payout
> lifecycle behind `payout.scheduled` / `payout.paid` is in
> [08 — Payouts and Reconciliation](08-payouts-and-reconciliation.md). The
> decision to make the ledger event-driven rather than synchronous is
> [ADR-004](10-architecture-decision-records.md#adr-004-event-driven-ledger-vs-synchronous-posting).

## 1. The envelope

Every domain event, regardless of type, is wrapped in a common envelope:

```
Event {
  id:    string   # "evt_..." prefixed snake id — globally unique, the idempotency key
  type:  string   # dotted event type, e.g. "payment.settled"
  ts:    string   # RFC-3339 UTC timestamp of when the event occurred
  data:  object   # type-specific payload; schema depends on `type`
}
```

Field rules:

- **`id`** is unique across all events for all time. It is generated by the
  producer (the gateway) and is the *only* thing consumers key idempotency on
  (§8). Two events describing "the same thing happened twice" must have different
  ids; two deliveries of "the same event" share one id.
- **`type`** is a stable, dotted string from the closed set in §2. Consumers
  switch on it. New event types may be added; existing ones are never repurposed.
- **`ts`** is RFC-3339 UTC (e.g. `2026-09-15T10:32:04Z`). It is the *event*
  time, not the delivery time.
- **`data`** carries `Money` objects as `{ amount_minor, currency }` (see
  [06 — Money Movement and Fees §6](06-money-movement-and-fees.md#6-currency-handling-rules)),
  IDs as prefixed snake strings, and timestamps as RFC-3339 UTC.

## 2. Event types at a glance

| `type`                | Producer | Primary consumer | Ledger effect |
| --------------------- | -------- | ---------------- | ------------- |
| `payment.authorized`  | gateway  | console projection | none (informational) |
| `payment.settled`     | gateway  | ledger `posting`   | posts the settlement entry |
| `refund.completed`    | gateway  | ledger `posting`   | posts the reversal entry |
| `payout.scheduled`    | gateway  | console projection | none (informational) |
| `payout.paid`         | gateway  | ledger `payouts`   | marks batch paid, debits `seller_payable` |

The **producer is always the gateway** — it owns the payment API edge and is the
only component that publishes events (spec: "gateway publishes → ledger
consumes; console reads projections"). The **ledger consumes** the accounting-
relevant events via `POST /internal/events`. The **console** reads *projections*
built from the event stream (it never consumes raw events to touch the
processor).

## 3. `payment.authorized`

The buyer's card was authorized for the charge. No money has moved into the
ledger yet — authorization is a hold, not a settlement. This event is
informational: it lets the console show a charge as `authorized` before it
settles.

**`data` schema:**

```
{
  charge_id:     string    # "chg_..."
  platform_id:   string    # "plat_..."
  seller_id:     string    # "sell_..."
  amount:        Money
  platform_fee:  Money
  processor_fee: Money
}
```

- **Producer:** gateway, after the `processor` adapter returns a successful
  authorization for `POST /v1/charges`.
- **Consumer:** console projection (Transactions screen). The ledger does **not**
  post anything on authorization — it waits for `payment.settled`. See
  [05 — Ledger Model and Invariants](05-ledger-model-and-invariants.md); postings
  happen on settlement, not authorization.
- **Ordering / causality:** `payment.authorized` for a charge always precedes
  `payment.settled` for that same charge. It is the first event in a charge's
  causal chain.
- **Idempotency:** keyed on `event.id`. A redelivered authorization updates no
  ledger state and is a projection no-op if already seen.

**Example (`chg_0001`):**

```json
{
  "id": "evt_authorized_0001",
  "type": "payment.authorized",
  "ts": "2026-09-15T10:32:01Z",
  "data": {
    "charge_id": "chg_0001",
    "platform_id": "plat_marisqueira",
    "seller_id": "sell_atelier",
    "amount":        { "amount_minor": 12000, "currency": "EUR" },
    "platform_fee":  { "amount_minor": 348,   "currency": "EUR" },
    "processor_fee": { "amount_minor": 205,   "currency": "EUR" }
  }
}
```

## 4. `payment.settled`

The authorized funds have cleared from the card network. **This is the event that
drives the ledger's settlement posting** (spec: "→ ledger posts the settlement
entry").

**`data` schema (identical shape to `payment.authorized`):**

```
{
  charge_id:     string
  platform_id:   string
  seller_id:     string
  amount:        Money    # A
  platform_fee:  Money    # P, computed by gateway `pricing`
  processor_fee: Money    # F, quoted by the processor adapter
}
```

- **Producer:** gateway, once the `processor` adapter confirms the charge has
  settled. The `platform_fee` and `processor_fee` carried here are the final
  authoritative amounts; the ledger records them verbatim and does not recompute
  (see [06 — Money Movement and Fees §2.2](06-money-movement-and-fees.md#22-where-the-computation-lives)).
- **Consumer:** ledger `posting` module. On consumption it posts the four-line
  settlement entry (`DEBIT processor_clearing A`, `CREDIT platform_revenue P`,
  `CREDIT processor_fees F`, `CREDIT seller_payable:{seller} N=A−P−F`). See the
  full worked posting in
  [06 — Money Movement and Fees §5](06-money-movement-and-fees.md#5-fully-worked-example--chg_0001-settlement).
- **Ordering / causality:** always follows `payment.authorized` for the same
  charge; always precedes any `refund.completed` for that charge. Per the spec,
  "events for a single charge are causally ordered."
- **Idempotency:** keyed on `event.id`. The ledger records `event_id` on the
  resulting `JournalEntry`; redelivery finds the existing entry and posts nothing
  (see [05 — Ledger Model and Invariants §4](05-ledger-model-and-invariants.md#4-journalentry-and-journalline)).

**Example (`chg_0001`):**

```json
{
  "id": "evt_settled_0001",
  "type": "payment.settled",
  "ts": "2026-09-15T10:32:04Z",
  "data": {
    "charge_id": "chg_0001",
    "platform_id": "plat_marisqueira",
    "seller_id": "sell_atelier",
    "amount":        { "amount_minor": 12000, "currency": "EUR" },
    "platform_fee":  { "amount_minor": 348,   "currency": "EUR" },
    "processor_fee": { "amount_minor": 205,   "currency": "EUR" }
  }
}
```

This produces `jrnl_stl_0001` with seller net `11447` (€114.47) credited to
`seller_payable:sell_atelier`.

## 5. `refund.completed`

A refund against a charge has completed at the processor. **This event drives the
ledger's reversal posting** (spec: "→ ledger posts the reversal entry").

**`data` schema:**

```
{
  refund_id:  string    # "rfnd_..."
  charge_id:  string    # "chg_..." the charge being refunded
  amount:     Money      # R, the refunded amount (full or partial)
}
```

Note the schema carries only `refund_id`, `charge_id`, and `amount`. The ledger
already knows the original charge's amounts (from the settlement entry) and
derives the proportional fee give-back itself — the event does not restate the
fees. This keeps the refund event minimal and authoritative on the one thing only
the gateway knows: how much was actually refunded.

- **Producer:** gateway refund handler, after `processor.refund` succeeds. This
  is the tail of the cross-repo refund flow: console `RefundButton` → BFF
  `refunds` route → gateway `POST /v1/charges/{id}/refunds` → `processor.refund`
  → emit `refund.completed`.
- **Consumer:** ledger `posting` module. It computes the proportional fee
  give-back with banker's rounding and posts the mirror-image reversal entry
  (`DEBIT seller_payable`, `DEBIT platform_revenue`, `DEBIT processor_fees`,
  `CREDIT processor_clearing R`). Full arithmetic in
  [06 — Money Movement and Fees §4](06-money-movement-and-fees.md#4-the-refund-give-back).
- **Ordering / causality:** follows `payment.settled` for the charge. Multiple
  partial refunds against one charge are causally ordered among themselves.
- **Idempotency:** keyed on `event.id`. Redelivery of the same refund event posts
  no second reversal. (Two *different* partial refunds are two different events
  with different ids and both post.)

**Example — full refund of `chg_0001`:**

```json
{
  "id": "evt_refund_0001",
  "type": "refund.completed",
  "ts": "2026-09-16T09:05:12Z",
  "data": {
    "refund_id": "rfnd_0001",
    "charge_id": "chg_0001",
    "amount": { "amount_minor": 12000, "currency": "EUR" }
  }
}
```

This posts `jrnl_rev_0001`, the exact mirror of `jrnl_stl_0001`, returning every
account for the charge to zero (see
[05 — Ledger Model and Invariants §9](05-ledger-model-and-invariants.md#9-worked-example--full-refund-reversal-of-chg_0001)).

**Example — partial refund (€40.00) of `chg_0001`:**

```json
{
  "id": "evt_refund_0001p",
  "type": "refund.completed",
  "ts": "2026-09-16T09:05:12Z",
  "data": {
    "refund_id": "rfnd_0001p",
    "charge_id": "chg_0001",
    "amount": { "amount_minor": 4000, "currency": "EUR" }
  }
}
```

This posts a reversal of `3816` clawed back from `seller_payable:sell_atelier`,
`116` off `platform_revenue`, `68` off `processor_fees`, and `4000` credited to
`processor_clearing` — worked in
[06 — Money Movement and Fees §4.2](06-money-movement-and-fees.md#42-partial-refund-worked).

## 6. `payout.scheduled`

A payout batch has been scheduled to move a seller's payable balance to their
bank. Informational for the ledger's *posting* path — no journal entry results
from scheduling; the movement is posted only when the payout is actually paid
(§7).

**`data` schema:**

```
{
  batch_id:      string    # "pyt_..."
  seller_id:     string    # "sell_..."
  amount:        Money      # the batch amount drawn from seller_payable
  scheduled_for: string     # RFC-3339 UTC time the payout is scheduled to execute
}
```

- **Producer:** gateway, when a payout batch is created / accepted for execution.
  (The batch itself is *built* by ledger `payouts` from the `seller_payable`
  balance, then executed via gateway `POST /v1/payouts`; the gateway emits this
  event as the batch enters the scheduled state — see
  [08 — Payouts and Reconciliation](08-payouts-and-reconciliation.md).)
- **Consumer:** console projection (Payouts screen), which shows upcoming
  payouts. The ledger tracks the batch's `scheduled` status but posts no journal
  entry yet.
- **Ordering / causality:** `payout.scheduled` for a batch precedes
  `payout.paid` for the same batch.
- **Idempotency:** keyed on `event.id`. Redelivery does not create a second
  batch.

**Example — scheduled payout of `sell_atelier`'s balance:**

```json
{
  "id": "evt_payout_sched_0001",
  "type": "payout.scheduled",
  "ts": "2026-09-17T00:00:00Z",
  "data": {
    "batch_id": "pyt_0001",
    "seller_id": "sell_atelier",
    "amount": { "amount_minor": 11447, "currency": "EUR" },
    "scheduled_for": "2026-09-18T08:00:00Z"
  }
}
```

The `11447` here is Atelier Costa's `seller_payable` balance after `chg_0001`
settled and before any refund — €114.47.

## 7. `payout.paid`

The processor has disbursed the payout batch to the seller's bank. **This event
drives the ledger to mark the batch paid and debit `seller_payable`** (spec: "→
ledger marks the batch paid and debits seller_payable").

**`data` schema:**

```
{
  batch_id:     string    # "pyt_..."
  seller_id:    string    # "sell_..."
  amount:       Money      # the disbursed amount
  processor_ref: string     # the processor's reference for the disbursement
}
```

- **Producer:** gateway, after the processor confirms the payout has been paid.
  The `processor_ref` is the disbursement reference used later during
  reconciliation to match the ledger movement to the processor's record.
- **Consumer:** ledger `payouts` (marks the `PayoutBatch` `paid`) and `posting`
  (posts the payout entry that debits `seller_payable:{seller}` and credits
  `processor_clearing` for the disbursed amount, discharging the liability). See
  [08 — Payouts and Reconciliation](08-payouts-and-reconciliation.md).
- **Ordering / causality:** always follows `payout.scheduled` for the same
  batch. A batch cannot be paid before it is scheduled.
- **Idempotency:** keyed on `event.id`. Redelivery does not double-debit
  `seller_payable`; the batch is already `paid` and the entry already exists.

**Example — `pyt_0001` paid:**

```json
{
  "id": "evt_payout_paid_0001",
  "type": "payout.paid",
  "ts": "2026-09-18T08:00:03Z",
  "data": {
    "batch_id": "pyt_0001",
    "seller_id": "sell_atelier",
    "amount": { "amount_minor": 11447, "currency": "EUR" },
    "processor_ref": "po_ref_atelier_0918"
  }
}
```

On consuming this, the ledger posts:

```
JournalEntry jrnl_pay_0001  (kind=payout, currency=EUR, event_id=evt_payout_paid_0001)

  DEBIT  seller_payable:sell_atelier    11447    # discharge what we owed Atelier Costa
  CREDIT processor_clearing             11447    # €114.47 leaves clearing to the bank
```

which balances (`11447 == 11447`) and drives `seller_payable:sell_atelier` back
to zero — Atelier Costa has been fully paid out for `chg_0001`.

## 8. Idempotency and delivery semantics

Event delivery to the ledger is **at-least-once**. A producer may redeliver an
event after a transient failure, and a consumer may see the same event more than
once. Correctness under redelivery rests entirely on **idempotency keyed on
`event.id`**:

- The ledger stamps every `JournalEntry` with the `event_id` that produced it.
  Before posting, it checks whether an entry already exists for that `event_id`;
  if so, it returns success without posting again. This makes
  `POST /internal/events` safe to call repeatedly with the same envelope.
- Projections in the console likewise dedupe on `event.id`.
- Because idempotency is on `event.id` and not on a business key, two genuinely
  distinct movements (e.g. two partial refunds of the same charge) are never
  collapsed — they carry different ids and both take effect.

Do **not** confuse this event-level idempotency with the gateway's
**`Idempotency-Key` header** on `POST /v1/charges`. Those are two different
mechanisms at two different layers: the header prevents a *duplicate charge* from
being created at the API edge (gateway `idempotency` package;
[ADR-003](10-architecture-decision-records.md#adr-003-idempotency-keys-on-charges)),
while `event.id` idempotency prevents a *duplicate posting* in the ledger. A
single charge created once can still emit a `payment.settled` event that gets
delivered twice — the header wouldn't help there; `event.id` dedupe does.

## 9. Ordering and causality summary

Per-charge and per-batch causal chains, in order:

```
charge lifecycle:   payment.authorized  →  payment.settled  →  refund.completed*
payout lifecycle:   payout.scheduled    →  payout.paid
```

Guarantees:

- Events for a **single charge** are causally ordered: `authorized` before
  `settled` before any `refunded`. The ledger relies on this — it cannot post a
  reversal for a charge it hasn't settled.
- Events for a **single payout batch** are ordered: `scheduled` before `paid`.
- There is **no** global total order across different charges or different
  sellers, and consumers must not assume one. Ordering is only guaranteed within
  a single causal chain.
- Combined with `event.id` idempotency, in-chain ordering is enough to keep the
  ledger correct without a global sequencer.

## 10. Quick reference — `data` fields per type

| type | data fields |
| ---- | ----------- |
| `payment.authorized` | `charge_id, platform_id, seller_id, amount, platform_fee, processor_fee` |
| `payment.settled` | `charge_id, platform_id, seller_id, amount, platform_fee, processor_fee` |
| `refund.completed` | `refund_id, charge_id, amount` |
| `payout.scheduled` | `batch_id, seller_id, amount, scheduled_for` |
| `payout.paid` | `batch_id, seller_id, amount, processor_ref` |

All events share the envelope `{ id, type, ts, data }`. All `Money` fields are
`{ amount_minor, currency }`. All ids are prefixed snake ids. All timestamps are
RFC-3339 UTC.
